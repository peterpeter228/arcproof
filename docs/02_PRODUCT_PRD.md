# ArcProof 详细开发 PRD

版本：1.0。日期：2026 年 10 月 20 日。受众：负责实施的 ChatGPT dot、其编码任务和独立审查任务。

## 1 产品定位

ArcProof 是面向已经使用 Arc 和 USDC 的开发者与小团队的发票直付原型。商户创建固定收款条件，付款人核对后付款，合约在同一笔交易中把金额转给商户并记录唯一付款凭证。任何人可以按交易和发票编号独立复核。

第一目标是得到真实、完整、诚实标注的可提交作品，争取 Arc Studio Microgrant。第二目标是验证是否有人愿意为单店支付集成或对账适配付费。没有验证之前，不建设交易平台、Agent 市场、通用收银 SaaS 或多链基础设施。

初版是**公开可审查的小额演示应用**。单张发票最多 1 USDC，商业集成需要另外界定客户范围并复审；不能用这份原型的测试结果宣称已经通过独立专业审计。

## 2 成功与失败的定义

### 产品完成

从干净环境安装、运行测试和构建成功；Studio 项目可追溯；测试网真实跑通创建、付款、核验；主网由本人签名完成获授权的小额演示后，收据能由独立页面重算。没有主网授权或资金时，交付部署就绪状态，不能标为主网完成。

### 商业成功

Grant 只有实际到账才算资助现金；集成业务只有实际客户付款才算付费信号，确认收入还取决于约定交付。自有钱包互转、交易量、点赞、测试数据和报价均不计收入。

### 应停止

Grant 专属路径在 G0 无法核实资格或入口时保持暂停；用户另行授权的免费原型不受该资格阻塞。其他停止条件：只剩不够完成必要验证的时间；Studio 来源要求无法满足；资金相关测试不通过；新增支出超限；需要转成托管或复杂后端才能演示；或者商业验证窗口内没有实际付费信号。具体门槛见第 18 节。

## 3 用户及核心场景

| 角色 | 待验证的需求假设 | 本版完成的工作 |
| --- | --- | --- |
| Arc 项目开发者或小商户 | 收到同金额转账后难以对应订单；截图难核验 | 创建带固定条件的付款请求，按发票查看收据 |
| 付款人 | 确认付给谁、付多少、用哪条链，避免同一请求重付 | 核对链上条件、签一次付款交易、得到可复核凭证 |
| 评委或集成买方 | 判断应用是否真实工作、能否迁入自己的项目 | 不连钱包查看演示证据、源码、网络与验证过程 |

客户画像是本次设计假设，未做真实访谈。不会假定普通商家有 Arc 钱包或愿意迁入新链。

## 5 明确删除的范围

不实现 escrow、存款账户、待验收释放、退款池、争议仲裁、AI 质量裁决、超时付款、分期、拆单、多币种、跨链、x402、ERC-8183、Agent 自主支出、平台抽成、邀请返佣、发币、DEX、会员系统、排行榜、CRM、营销消息自动发送。

到期只表示该未付请求不能再付款，不会触发转账。退货退款若发生，由交易双方在本应用外另行处理；本版不声称提供消费者保护或履约裁定。

## 6 核心体验

### 6.1 商户开票

连接钱包后显示当前 chainId 与创建者地址。填写金额、有效期和可选的公开短标题。默认有效期为 24 小时；合约限制创建时有效期在未来且不超过 7 天。金额必须是普通十进制字符串，最多 6 位小数，范围 0.000001 至 1 USDC。

P0 创建界面始终传零值 termsHash，明确表示没有附加条款摘要。可选短标题仅在本地保存和选择性分享，按未签名、未绑定到链上条款的纯文本展示，不作为付款凭证的一部分。不放姓名、邮箱、订单明细或客户身份资料。合约保留 bytes32 字段，但本版不设计非零摘要的序列化协议；读取非零 termsHash 时标记 UNSUPPORTED_TERMS 并禁止从本界面付款，已有付款仍可只读核实。哈希不能保证低熵文本的保密性。

签名后先记住交易哈希，等链上成功事件返回发票 ID 再生成链接。不要因为预测 nonce 就提前把一个未创建 ID 显示为有效付款请求。创建失败不生成可付款链接。

### 6.2 付款人支付

付款页无需登录或先签消息即可读取发票。展示完整收款地址、金额、网络、到期时间及状态。只有点击“连接钱包并付款”后才请求钱包访问。

在请求签名的当下重新读取链上条件和当前网络，重做模拟及费用估计。金额、收款人、合约地址都由可信配置和链上状态提供，不能由 URL 参数覆盖。原生 USDC 的 value 使用 18 位精度；支付调用不要求 ERC-20 approve、Permit 或无限授权。

付款准备对象绑定 chainId、deploymentId、contractAddress、payer、invoiceId、value、calldata 和 connectionVersion。账户、链、发票或部署切换时，立即使旧准备对象和未返回的异步结果失效；钱包调用前再次比较这些字段。广播请求显式固定 from、chainId、to、data、value，不临时拼接另一个当前账户。请求已经交给钱包后，应用不能保证撤销；最终结果依实际交易核实。

任意付款人都可支付发票，因此凭证上显示实际付款地址；不能把发票创建者、客户名称或当前浏览器地址误记为 payer。相同发票的并发付款只有第一笔成功，另一笔可能仍消耗网络费用。

### 6.3 确认与收据

链上成功后先展示交易已包含；完成最终性和事件核验后才显示“已验证付款”。收据包括网络、合约、发票 ID、双方地址、金额、时间、区块哈希、交易哈希、验证规则版本与费用。收据证明发生过付款，不证明货物交付、劳动完成或争议已解决。

另开一个干净页面，凭含部署身份的付款链接即可恢复收据；也可输入发票定位信息与 tx hash 直接核实。链上 paidBlockNumber 指向付款区块，缺少 tx hash 时只查询该区块、本部署和该发票的 InvoicePaid 日志以恢复 hash，再走完整验证器。匹配必须恰好一条；零条或多条均待核实。下载 JSON 中的 verified 字段只是缓存，不是可信证明，导入后必须重算。

## 7 状态设计

发票业务状态和某次钱包操作状态分开存放。

| 发票状态 | 判断来源 | 可执行操作 |
| --- | --- | --- |
| NOT_FOUND | 指定合约不存在该 ID | 返回重新核对链接 |
| OPEN | 发票存在、未付，区块时间早于 expiresAt | 可请求付款 |
| PAID | 链上 paid 已置位，付款凭证待另行核验 | 查看和验证收据，不显示支付按钮 |
| EXPIRED | 发票未付且区块时间大于等于 expiresAt | 查看只读信息，商户可新建另一张 |
| UNKNOWN | RPC 失败、网络不一致、状态无法判断 | 重试读取，禁止依据旧缓存付款 |

钱包操作状态使用 IDLE、AWAITING_SIGNATURE、SUBMITTED、INCLUDED、VERIFIED、REJECTED、FAILED、UNKNOWN。FAILED 只说明这一次调用失败，不把发票永久标成失败。刷新页面后先恢复 tx hash 并查链，不自动重发付款。

区块时间用于合约有效性判断，客户端时间仅用于近似倒计时。到期临界时重新模拟；过期边界由合约决定。已付款发票在时间过期后仍是 PAID。

## 8 页面与视觉规格

| 页面 | 内容与主操作 |
| --- | --- |
| 首页 `/` | 一句话说明、三步演示、打开工作台、查看独立凭证；不展示虚构商户或收入 |
| 工作台 `/#/app` | 网络和地址、发票列表、新建表单；先展示最近 20 条 |
| 付款页 `/#/pay/:chainId/:deploymentId/:invoiceId` | 固定条款、网络费用、收款地址、状态、单一付款按钮 |
| 收据页 `/#/receipt/:chainId/:deploymentId/:invoiceId?tx=...` | 凭证校验、浏览器链接、JSON/CSV/打印；tx 可从付款区块恢复 |
| 证据页 `/#/evidence` | Studio 项目、源码提交、测试结果、已验证主网自测记录与视频 |

用 hash 路由是初版静态托管的有意选择，避免子路径刷新依赖服务器重写。若部署平台已验证 SPA fallback，可以改成普通路径，但必须通过直接打开深链的测试。

界面默认英文，文案清晰短句；开发文档中文。浅色背景、深灰正文、一种蓝绿色强调色；金额和地址使用易区分字符的等宽字体，正文至少 16px。桌面 1280px、移动 390px 验证无横向滚动；错误信息不能仅靠颜色。键盘可操作，焦点明显，连接钱包前不弹多余对话框。

不做大面积加密风格渐变、动画背景、生成式配图或复杂仪表盘。技术字段在收据和详情内可见，付款确认中的网络、金额与收款人必须直接展示。

## 9 技术路线

**主线：保留 Arc Studio 的 Vite + Foundry 结构。** 前端 React、TypeScript、Vite；钱包采用 viem 加轻量 wagmi 连接；合约 Solidity、OpenZeppelin ReentrancyGuard、Foundry。金额与凭证解析写成与 UI 无关的纯函数。

Studio CLI 官方支持编码 Agent 通过结构化命令调用并拉回代码，sandbox 使用 Vite 与 Foundry。不要先在别处生成全部应用再补 Studio 截图假装来源符合要求。[S06]

P0 不需要后端、数据库、登录、Supabase、Redis、LLM API 或定时服务。链上状态保存不可修改的发票，localStorage 只保存非敏感草稿、用户偏好和未确认 tx hash。代码使用现成依赖并锁版本，不维护自制密码学或钱包 SDK。

静态托管首选 dot 当前已可用的 Sites：构建输出 `dist`，按当前 Sites 技能同步源码和部署。若 Sites 不可用或产物不兼容，只选择已有授权的静态托管渠道，不购买新服务或迁入全栈框架。静态主页面必须能被未登录评委访问；私有预览只用于内部验收。[S24–S25]

## 10 链配置与单位

| 参数 | Arc Mainnet | Arc Testnet |
| --- | --- | --- |
| chainId | 5042 | 5042002 |
| RPC | https://rpc.mainnet.arc.io | https://rpc.testnet.arc.io |
| 浏览器 | https://explorer.arc.io | https://explorer.testnet.arc.io |
| 原生资产 | USDC，18 位小数 | 测试 USDC，18 位小数 |
| ERC-20 接口 | 0x3600000000000000000000000000000000000000，6 位小数 | 同地址，6 位小数 |

以上是官方文档快照，执行时重新核对并锁定。项目合约地址目前未知，`deployments.json` 必须用 null，不能借用官方其他合约地址冒充本应用部署。[S07–S08]

每个部署有不可变 deploymentId，使用小写字母、数字和连字符，最长64字符；`chainId + deploymentId` 唯一对应一个已核实合约。manifest 追加新部署，保留旧身份和旧地址，不能用重新部署的地址覆盖旧记录。路由、缓存、发票读取、付款准备及收据均携带部署身份。同链两个部署的旧链接各自可恢复；URL 带来的未知 deploymentId 或任意地址不得获得签名权限。

统一金额规则：

1. 用户输入按字符串解析为整数 microUSDC，禁止浮点、科学计数法、负数、逗号小数和超过 6 位精度。
2. nativeAmount = microUSDC × 1,000,000,000,000。
3. 0.20 USDC = 200,000 microUSDC = 200,000,000,000,000,000 native units。
4. 金额落库、URL 或 JSON 中用十进制整数字符串，不把 BigInt 转为 Number。
5. gas 单独按原生 18 位单位计算；原生余额和 ERC-20 余额是同一底层 USDC，不能相加。

原型走原生 value 的原子转付路径。官方 ERC-20 同一转账可能同时发 6 位和 18 位两条日志，本项目只消费白名单系统地址的 18 位流。不是收集所有名为 Transfer 的事件后求和。[S10]

## 11 合约产品约束

合约名建议 ArcProofInvoices。创建者即收款人，不能替别人创建收款地址。invoiceId 的唯一派生规则为 `keccak256(abi.encode(uint256 chainId, address contract, address merchant, uint256 nonce))`，禁止改成 encodePacked 或字符串拼接。初始 nextNonce=0，表示下一个未使用的 nonce；成功创建后递增。不同网络、商户和部署分别有独立身份。

创建后不可变的字段包括 merchant、amountNative、expiresAt 和 termsHash。只允许 paid 从 false 变为 true 一次。不设取消函数，未付款错误发票可等待到期后重新创建；取消、回滚修改和作废签名不是本版需求。

成功付款保存 payer、paidAt 和 paidBlockNumber；未付时后二者为0，付款时分别取 block.timestamp 与 block.number。getInvoice 返回这些字段。链上不存无法直接取得的交易 hash，前端用付款区块中的特定事件恢复它。

payInvoice 要求记录存在、未付款、未到期、msg.value 精确等于金额。先做检查和状态更新，再向固定商户执行外部转账；createInvoice 和 payInvoice 使用同一个成熟 nonReentrant 保护。商户拒收或发生错误时整笔 revert，状态与转账一同回滚，但调用者可能承担网络费用。

付款开始记录 balanceBefore=balance-msg.value，转付返回后要求余额恢复到 balanceBefore；回调期间强塞新余额则整笔回滚。正常成功付款不增加合约保留余额，也不允许动用意外余额补足本次付款。合约可能收到强制转入的资产，因此不得写“余额永远为零”。无管理员、升级、提取、救援、累计余额、支付后退款或隐藏费用接口。完整函数、事件和安全要求见 CONTRACT_SPEC.md。

P0 UI 正式支持普通 EOA；Safe、账户抽象和 EIP-7702 委托账户不列入已验证范围。合约层仍要用恶意收款合约测试重入和拒收，不能用 UI 限制代替合约正确性。

## 12 前端数据与接口边界

建议文件边界：`src/chain/config.ts`、`src/chain/readInvoice.ts`、`src/chain/preparePayment.ts`、`src/chain/verifyReceipt.ts`、`src/domain/amounts.ts`、`src/domain/invoiceId.ts`、`src/domain/types.ts`。UI 不直接拼 calldata。

主要接口：

- `parseAmount(text): Result<{micro: bigint, native: bigint}>`
- `readInvoice(chainId, deploymentId, invoiceId): InvoiceReadResult`
- `preparePayment(chainId, deploymentId, invoiceId, payer, connectionVersion): PreparedPayment`，内部重读、检查白名单、估费及模拟；输出绑定上下文，不作为可重复使用的授权。
- `recoverPaymentHash(chainId, deploymentId, invoiceId): PaymentLocatorResult`，只读 stored paidBlockNumber，再取该区块匹配事件。
- `verifyReceipt(chainId, deploymentId, invoiceId, txHash): VerificationResult`
- `listMerchantInvoices(chainId, deploymentId, merchant, cursor): InvoicePage`

这些是模块接口，不要求创建 HTTP 服务。调用错误统一有稳定代码和人类可读文本，例如 WRONG_CHAIN、INVALID_AMOUNT、INVOICE_EXPIRED、ALREADY_PAID、RPC_UNAVAILABLE、UNVERIFIED_DEPLOYMENT、RECEIPT_MISMATCH。

商户列表读取 nextNonce=N，已创建 nonce 范围为 [0,N)，最近页从 N−1 向前最多取20条；N=0显示空列表。按唯一ABI编码计算对应 invoiceId，向前分页不遗漏、不重复。每张已付发票可凭 paidBlockNumber 恢复收据，不依赖浏览器历史。不要从创世区块不停抓 logs。公共 RPC 调用批次和并发受限，初始并发最多3；同一发票短缓存，付款前强制刷新；网络故障不能显示伪成功。异步请求携带连接版本，旧版本返回值不得恢复支付按钮。

## 13 收据验证算法

验证器必须从固定的受信配置选择 RPC 与本项目合约，先确认 RPC 的 chainId，再读取交易、receipt、区块及发票状态。

必须满足：receipt.status 成功；交易 to 是本部署；输入 selector 和参数是该 invoice 的 payInvoice；value 等于固定金额；交易 from 与 InvoicePaid 的 payer 对应；事件由本项目地址发出，invoiceId、merchant、amount 匹配；链上 paid 为 true、paidBlockNumber 等于 receipt 的 blockNumber、paidAt 等于所核实区块时间。拒绝用任意同名事件或同金额另一笔交易替代。

在 Arc 实测确定系统日志和该调用的对应关系，校验项目合约向 merchant 的本次原生金额转移。若接收方又立即向外转账，不把最终余额差误当支付失败；但本版演示收款方使用普通 EOA，以保持证据清楚。

Arc 官方说明已提交区块具有确定性最终性，不需要额外的 Ethereum 式确认窗口。[S27] 本版核实成功 receipt 与一致的已提交区块哈希即可完成正常链上最终性判断；INCLUDED 仅表示应用尚未完成自身凭证核验，不是 Arc 协议的中间最终性状态。RPC 不一致时使用第二个已核实端点交叉读取并保持 UNKNOWN；不要把等待任意 N 个区块当作修复数据冲突的方法。

交易唯一键为 chainId + txHash + 本应用事件 logIndex。发票状态的唯一性在链上保证，缓存导出不得产生第二次收入。给验证器坏事件、错链、伪合约、错误金额和失败 receipt 应全拒绝。

导出必须含 deploymentId、contractAddress、paidBlockNumber 和 paymentLogIndex，以及合约规格规定的其余字段；大整数均用十进制字符串。paymentLogIndex 来自真实 receipt 中选定的 InvoicePaid，不能用数组下标猜测它。

## 14 数据可靠性与隐私

P0 不引入非零 termsHash 协议：创建时固定零摘要，可选标题明确为不可信、未绑定的分享文本。读到非零摘要时禁止本界面发起付款，显示“本版不支持核对附加条款”；不能默默省略条款让用户付款。已有付款的只读链上验证不因正文缺失而编造交付结论。公开链本身可见的地址与金额不能宣传为隐私支付。

草稿备份 JSON 中记录 schemaVersion、chainId、deploymentId 和合约地址，导入先验证类型、长度、金额和地址，不执行 HTML、脚本或模板。分享标题最多80个Unicode码点并按纯文本渲染，不用危险 HTML；不对标题宣称真实性。

生产构建禁止嵌入钱包私钥、助记词、登录 token 或服务端密钥。钱包由本人控制；不能把用于测试的新私钥放入源码包当成主网钱包。Foundry 测试账户明确仅限本地，绝不向其注入真实资产。

## 15 错误与运行指标

| 场景 | 预期行为 |
| --- | --- |
| 拒绝连接或签名 | 回到可重试状态，未创建/支付，不责怪用户 |
| 网络错误 | 保留已有 tx hash，标记待核实，先查链再决定是否可再次发起 |
| 余额不足 | 展示金额与估计费用缺口，不自动买币、桥接或扣其他资产 |
| 发票在确认期间被支付 | 更新为已付款，停止该次付款准备 |
| 前端金额被改写 | 以链上金额比较并阻止请求，不替用户悄悄换金额 |
| 收款人拒收 | 明确本次付款失败，发票仍未支付，保留错误和已消耗费用 |
| 不支持的账户类型 | 说明本版支持范围，不引导关闭钱包防护 |
| 未核实合约配置 | 只读诊断，不允许签名 |

体验目标是设计验收阈值：固定网络条件下首次页面可交互尽量在 3 秒内；RPC 正常时从已最终确认到界面验证完成目标 5 秒内。记录环境、样本和实际分布，不承诺网络或共识 SLA。主网费用逐笔估算，不硬编码“每笔不到一美分”。
