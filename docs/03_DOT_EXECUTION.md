# dot 执行与交付手册

## 1 为什么这样适配 dot

OpenAI 官方说明 dot 能在云端持续工作，委派后台任务，并通过已连接的应用和开发环境推进软件工作；其本地电脑连接和云端浏览器是不同环境。不能假定 Windows 浏览器里已经登录的钱包、GitHub 或 Arc Studio 会自动出现在 dot 云端。[S22–S23]

本项目把 dot 当项目负责人，让它维护一个明确状态文件、调用 Arc Studio、安排独立审查和汇总证据。产品运行时没有 LLM，构建工具能力也不包装成给最终用户的产品功能。

## 2 首个工作段

先读本包而非重写 PRD。建立新工作目录，识别是否已有同名项目及变更，不覆盖用户其他工程。若使用现有 GitHub 仓库，先记录实际读取权限、分支、HEAD 和工作区状态；不能把此前其他仓库权限当作本仓库权限。

在 G0 中并行做可独立的只读工作：正式活动条款、Studio CLI 与登录能力、开发环境和工具版本。适格性所需本人资料只收集真正必要的部分，不从 IP、语言或账号时区猜。证据字段见 evidence/gate.json。

G0 不通过时，不生成新的资金合约。输出具体未闭合项与剩余材料；不要因网页抓取 405 就宣布活动不存在，也不要绕过站点的权限或验证。

## 3 运行环境探测

检查实际可用的 Node、包管理器、Git、Foundry、Arc Studio CLI、网页测试能力、静态托管和 GitHub 工具。只输出版本和是否可用，不打印完整环境变量或凭据。

Arc Studio CLI 文档最低要求 Node 20，实际版本以可用且仍受支持的运行时为准。记录 `node --version`、所用包管理器版本、`forge --version`、Solidity 编译器与依赖锁文件。只保留一种包管理器。

缺少工具时优先在允许的项目/工具目录安装官方依赖，不默认要求管理员权限。若环境不具备某项测试能力，记录 blocked 和影响，不假称做过 Windows 钱包真机测试。CLI、SDK 和命令在执行当日用官方文档与 --help 校验，不盲目执行材料里的历史样例。

## 4 Studio 与 dot 的协作边界

用官方 Studio 登录流程。账号已经授权就复用，不再要求同一授权；没有会话时走私密登录或本人接管，不在聊天粘贴 token。

把 prompts/ARC_STUDIO_BUILD.txt 作为起点，附本包合约规格文件作为上下文。官方 CLI 可用以下模式驱动，具体选项由当前版本 --help 复核：

```text
arc-studio run --prompt-file prompts/ARC_STUDIO_BUILD.txt --session arcproof-p0 --output json
arc-studio pull --session arcproof-p0 --out ./studio-export
```

长任务用已支持的 detach/attach 保留连续执行，避免断开连接造成取消；每段有超时和预算。提示正文保持小于官方 10,000 字符限制，大规格以 --file 引用，不把整包塞入一个提示。

保存返回的真实 app/session/project URL、状态和导出清单。completed 只表示这一回合完成，deployments 或 finalText 是 Agent 输出，需要链上验证。needs_input 时由 dot 根据既定规格回答普通实现问题；budget_exceeded 时保存结果并停止超预算调用，不自动付费扩容。[S06]

Studio 原始合约和界面完成后拉回独立目录，检查 diff、依赖与实际测试。代码修正要保留出处和变更轨迹，必要时回 Studio 同步并记录。不要为了来源要求抹掉 dot 修复的痕迹。

## 5 可并行的三个工作任务

| 任务 | 输入 | 所有权 | 交付 |
| --- | --- | --- | --- |
| 合约实现 | CONTRACT_SPEC、金额与状态约束 | contracts 与合约测试 | 小合约、ABI、Foundry结果、未决风险 |
| 前端实现 | PRD、固定ABI、design规范 | src和静态样式 | 工作台、付款、收据、导出与异常交互 |
| 独立验收 | 同一提交源码、测试矩阵、实际RPC证据 | 只读代码，独立报告 | 可复现缺陷、等级、验证遗漏 |

先定 ABI 再让前端接入；不存在 ABI 时可以用明确标注的 fixture 做界面，接入前必须删除对假成功的依赖。合约作者不能同时充当唯一审查者。没有可用子任务工具就按同一顺序执行，不要求安装编排平台。

Root 维护同一需求版本、合并和证据。不要自动请求用户选择钱包库、代码风格或设计颜色。新需求超 P0 时记入冻结清单，不立刻实现。

## 6 命令与可复现性

最终仓库必须提供一条文档化的安装命令、一条本地开发命令、一条前端构建命令和 `forge test` 的实际执行入口。命令应来自实际生成的 package.json 和 foundry.toml，不在 README 中填尚不存在的 npm script。

静态产物由干净安装生成，第三方依赖锁版本；UI 使用导出的固定 ABI。对独立审查之后的代码修改必须重跑受影响的资金或证据测试。没有更改的部分不反复重跑无意义检查。

## 7 持久状态与恢复

每完成一个门槛或发生阻塞，写入：当前 commit；已通过的 gate；实际工时/费用；Studio session；最后运行的测试；已验证部署；下一具体动作；哪些结果仍未知。

恢复任务时按 STATUS、gate、git status、最近测试结果读取，核对已有部署后再推进。不要再次创建同一个 Studio 项目、仓库、Site 或部署，不重复执行付款。拿不准某动作是否成功时先只读核实，不能靠重试交易探测。

在当前用户主动任务里持续推进，不额外创建长期扫描、自动报名、自动推广或周期任务。本包的日后检查是执行计划；如果用户要求 dot 持续跟踪结果，再使用实际可用的任务机制。

## 8 授权的最后一步

缺少公开或链上动作授权时，先完成下列可审查内容：

- 具体源码提交、构建摘要、测试结果和未审计声明。
- 计划公开的页面、仓库和文件范围。
- 主网 chainId、待部署字节码与费用估计。
- 每笔演示的调用、收款地址、金额、总费用上限及操作顺序。
- 最终英文提交文本、视频和真实证据链接；未产生的证据保持空。

然后仅说明缺少哪一动作授权及其影响。已有授权则直接在范围内继续。权限工具阻断时保留明确原因，不能扩大权限或宣称已经执行。申请涉及KYC时由本人通过正规流程完成；不要求发身份证到聊天。

## 9 每阶段汇报格式

```text
阶段：Gx
实际完成：能打开/运行/核验的结果
证据：commit、测试结果、URL或文件
未完成：明确的 not_run / failed / blocked
投入：本阶段和累计工时；实际新增现金；剩余额度
判断：继续下一段 / 停止该路径，及证据原因
下一动作：一个具体动作
```

不使用“开发90%”替代证据。最终完成报告要分别写本地、测试网、主网、公开可访问、已提交、获奖、到账；没有发生的阶段直写未完成。
